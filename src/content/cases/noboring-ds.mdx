## Без системы сборка интерфейсов держалась на одном человеке

Когда я пришёл, у команды был UI-kit без токенов и переменных. UX lead передавал мне черновые решения после тестов, я оформлял UI и прототипы. По мере роста ERP разные разделы использовали общие формы, таблицы и сценарии, и изменение одного правила могло затронуть множество экранов.

**Задача:** сделать сборку интерфейсов доступной команде и сохранить согласованность при изменениях.

| Кто пользуется системой | Что ему нужно |
|---|---|
| UX lead, UI-дизайнер | Собрать раздел из готовых компонентов и правил поведения |
| Фронтенд | Взять значения по имени токена и одинаково понимать свойства компонента |
| Ассистент через MCP | Собирать интерфейсы по правилам системы: 14 исходных инструкций в навыках |

## Токены выстроены как атомарная иерархия: тема переключается в одном слое

Атомарный подход (атомы → молекулы → организмы) описывает компоненты. Токены — уровень ниже: решения, из которых собираются сами атомы. Я разделил их на три коллекции, у каждой своя ответственность и свой набор режимов.

| Уровень | Коллекция | Что хранит | Режимы | Пример из библиотеки |
|---|---|---|---|---|
| Примитивы | .Primitives | Палитра и единицы без смысла | 1 | `Colors/Primary/500` = #1D23CD |
| Семантика | Semantic [Colors] | Роль цвета в интерфейсе | Light / Dark | `Colors/bg/action/default` |
| Компонентные | Components | Контракт компонента и его состояний | 1 (Default) | `Button/Color/Bg/primary/default` |

**Цепочки кнопки — из текущих alias-привязок библиотеки:**

- `Button/Color/Bg/primary/default` → `Colors/bg/action/default` → Light: `Primary/500` (#1D23CD) · Dark: `Primary/400` (#4B50D8)
- `Button/Color/Bg/secondary/default` → `Colors/bg/secondary/default` → Light: `Primary/50` (#E7E8F9) · Dark: `Primary/900` (#060728)
- `Button/Color/Text/primary/default` → `Colors/text/primary/-on-action-primary` → `Basic/-white` в обеих темах

**Решение: режимы темы есть только в семантике.** Компонентные токены имеют один режим и ссылаются на роли. Поэтому кнопка не знает о теме: смена Light/Dark переназначает роль на другой примитив, а компонент, его варианты и состояния не меняются. Вторичный фон в тёмной теме — не «чуть темнее», а другой конец шкалы (50 → 900): роль сохраняет контраст с текстом, а не оттенок.

<Figure src="/images/noboring-ds/ds-token-chain.gif" caption="**Смена темы по реальным alias-цепочкам Button:** переключаются только связи семантики, компонентные токены и сам компонент не меняются" />

**Как токены ложатся на атомарные уровни:**

- **Атом** — Button, Icon, Label: берут только компонентные токены.
- **Молекула** — Input = Label + .Field + Description: у каждой части свои токены, состояние живёт в .Field.
- **Организм** — форма, таблица, drawer: собираются из молекул и собственных цветов не задают.

**Цена:** имён и связей становится заметно больше. Их нужно последовательно именовать, проверять при изменениях и передавать фронтенду по общей модели.

<Figure src="/images/noboring-ds/ds-v3-token-modes-proof.png" caption="**Схема по текущим alias-привязкам:** примитивы → семантика → компонентный токен" />

## Поле собрано из частей: состояние живёт в .Field, подпись и пояснение переиспользуются

Input собирает Label, .Field и опциональный Description. Матрица взаимодействия (Default, Hover, Active, Filled, Error, Disabled) живёт внутри .Field. Поэтому изменение состояния не требует пересборки поля, а новая подпись не требует нового варианта. Ошибка тоже составная: .Field меняет состояние, Description получает тип Error.

Тот же принцип — в кнопках и иконках: глиф отделён от интерактивной обёртки, замена иконки не пересобирает hover и focus.

**Цена:** много опций требуют понятных названий и документации; наружу нужно раскрывать только те свойства, что нужны потребителю.

## В плотной ERP система описывает поведение, а не только внешний вид

Гайды описывают последовательность действий и ограничения. Ячейка таблицы различает наведение с правами и без прав на редактирование. В мультиселекте выбранные чипсы схлопываются в счётчик и раскрываются до 3,5 строк со скроллом: рабочая область сохраняется, а состав выбора остаётся доступным. Применённые фильтры при нехватке места схлопываются в кнопку.

**Цена:** часть значений скрыта до раскрытия, поэтому счётчик обязан показывать, что скрыто, и давать доступ к просмотру.

## Доступность: пользователи не различали статусы — чипсы переделал по замерам контраста

В чипсах со статусами текст был цветным и бледным — это тянулось с первого UI-kit, собранного на ранней версии Blank. Пользователи плохо различали статусы. Я замерил контраст каждой пары «текст / фон», сравнил решения Airtable, NocoDB и Notion и перевёл чипсы на тёмный текст поверх цветного фона: цвет остался признаком статуса, а читаемость перестала от него зависеть.

**Итог:** контраст новых чипсов — от 9,9:1 до 13,4:1, это выше порога WCAG AAA для обычного текста (7:1). В прошлой версии большинство чипсов не проходили проверку для обычного текста.

## Мост в код: токены через JSON и проверяемый контракт со Storybook

Архитектуру переменных согласовали с фронтендом: я передаю значения через JSON, разработчики применяют их по согласованным именам. Отдельно я собрал Storybook-стенд, который переводит свойства компонентов Figma в публичный API React-компонентов и проверяет их автоматически: Controls, темы, viewport, interaction и accessibility. Повторная проверка пропускает неизменившиеся компоненты.

## Система меняется от продуктовой потребности

File Card не подходила для inline editor, где уже были свои действия. Я выделил простой File Item — иконку и название — и зафиксировал изменение в Changes Log. Границу компонента уточнил конкретный сценарий, а не представление о полноте библиотеки.

**Спор о файлах в inline-полях.** По логике CRUDL файл в inline-поле прикреплялся только в отдельном режиме редактирования. Я настаивал, чтобы просмотр, прикрепление и удаление работали сразу, без перехода в режим. Команда выбрала вариант с режимом и выпустила его без теста. После релиза пользователи назвали его неудобным и попросили то, что я предлагал: прикреплять и редактировать сразу. Вывод для меня: если в команде спор о взаимодействии, аргументом должен быть короткий тест до релиза, а не правило или чьё-то мнение.

## Результат

Сборка UI и интерактивных макетов перестала быть сосредоточена только у меня: UX lead собирает интерфейсы из готовых компонентов и правил, разделы проектируются параллельно. На этой же системе я собираю прототипы в агентах Claude и Codex: агент берёт токены, компоненты и инструкции из навыков, поэтому прототип с вводом данных и рабочей логикой готов к обсуждению за день — раньше на прототип в Figma уходило 1–2 недели. Система применяется в ERP, например в разделе [встреч и задач](/cases/erp-meetings).

**Онбординг через систему.** К проекту подключали дизайнеров из другой команды — они входили в работу по документации DS: гайды, анатомия компонентов и правила токенов идут по отраслевым стандартам, поэтому отдельное обучение не понадобилось.

## Ограничения

Storybook — инженерный стенд для проверки согласованности API, а не production-библиотека фронтенда. Двусторонняя автоматическая синхронизация Figma и кода не заявлена. Срез принятия — один файл и один момент времени: динамику «до и после» системы я не замерял. Скорость сборки и сокращение дефектов в цифрах не замерялись.

## Что бы сделал иначе

- **Вести метрики принятия с первого релиза библиотеки.** Срез 2026 года показывает 87%, но без точки отсчёта нельзя показать, как система меняла практику команды.
- **Закрепить правила именования токенов в документации до роста библиотеки.** Три уровня дают много имён и связей; письменное правило проще проверять, чем устную договорённость.
- **Раскрывать наружу минимум свойств и добавлять по запросу.** История с File Item показала: границы компонента лучше задаёт реальный сценарий, чем стремление предусмотреть всё заранее.
